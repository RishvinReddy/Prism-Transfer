# PrismTransfer Protocol V3 Specification

## Overview
PrismTransfer V3 is a high-performance, unidirectional optical file transfer protocol relying on animated QR codes. It achieves maximum throughput by using a completely zero-copy binary framing design, ditching Base64 payload overhead, and employing Forward Error Correction (FEC) for immediate recovery.

## Binary Framing

Every V3 packet starts with a magic byte `0x50` ('P' in ASCII), followed by a Type byte.

### Manifest Packet (`Type 0x01`)
Describes the file being transferred and the structure of the incoming data stream.

**Binary Layout:**
* `0x00`: Magic Byte (`0x50`)
* `0x01`: Packet Type (`0x01` = Manifest)
* `0x02`: Version (`0x03`)
* `0x03-0x17`: Transfer ID (21 bytes, NanoID)
* `0x18-0x1B`: Reserved / Timestamp (4 bytes)
* `0x1C-0x23`: Original Uncompressed Size (8 bytes, uint64)
* `0x24-0x27`: Total Data Packets (4 bytes, uint32)
* `0x28-0x29`: Total Parity Packets (2 bytes, uint16)
* `0x2A-0x2B`: Parity Group Size (2 bytes, uint16)
* `0x2C`: Parity Algorithm (`0x00` = None, `0x01` = XOR)
* `0x2D-0x2E`: Filename Length (2 bytes, uint16)
* `...`: Filename String
* `...`: MIME Type Length (1 byte)
* `...`: MIME Type String

*Integrity relies on per-frame CRC32 and global Adler-32 decompression checksums. Global SHA-256 is intentionally omitted from the V3 Manifest to preserve space in low-density QR configurations.*

### Data & Parity Packets (`Type 0x02` & `Type 0x03`)
Contains compressed file chunks (Data) or erasure coding parity chunks (Parity).

**Binary Layout:**
* `0x00`: Magic Byte (`0x50`)
* `0x01`: Packet Type (`0x02` = Data, `0x03` = Parity)
* `0x02`: Version (`0x03`)
* `0x03-0x17`: Transfer ID (21 bytes, NanoID)
* `0x18-0x1B`: Packet Index (4 bytes, uint32)
* `0x1C-0x1F`: Total Packets in Stream (4 bytes, uint32)
* `0x20-0x23`: CRC32 of Payload (4 bytes, uint32)
* `0x24...`: Binary Payload

## Error Handling & Checksums
- **Payload Integrity:** Checked per packet via the `crc32` header. Packets that fail the CRC32 check are immediately discarded.
- **Protocol Compliance:** Packets with unknown Types, incorrect Versions, or mangled Headers are rejected early by the extraction logic.

## Parity Recovery
PrismTransfer V3 implements **XOR Parity** (Algorithm `0x01`):
1. **Grouping:** The stream is partitioned into groups of `N` data packets.
2. **Generation:** 1 Parity packet is generated per group by XORing the `N` data packets.
3. **Recovery:** If exactly 1 packet is lost in a group, the Receiver's background worker intercepts the gap and recovers the missing packet by XORing the `N-1` received packets against the Parity packet, reconstructing the lost packet byte-for-byte.

## Worker Architecture
Heavy lifting is executed via Web Workers to keep the UI Thread completely unblocked:
- `sender.worker.ts`: Handles file `fflate` compression, chunking, binary packet serialization, and Parity generation.
- `scanner.worker.ts`: Handles continuous raw video frame analysis via `jsQR`.
- `reconstruction.worker.ts`: Offloads parity math (XOR reconstruction) and final file decompression.

## Resume & State
- State is buffered into an abstract `StorageAdapter`. 
- In the browser environment, IndexedDB (`IndexedDBStorage`) is used to persist chunks between sessions.
- In automated test environments, `MemoryStorage` simulates the database.
- A transfer can be closed and resumed at any time, requiring the sender to resend the remaining chunks.

## Version Compatibility
V3 Receivers are explicitly backwards-compatible with V1 and V2 JSON-based senders via a graceful fallback within `serializer.ts`.
