# PrismTransfer Protocol

PrismTransfer operates over a unidirectional optical channel using animated QR codes. The protocol is designed to be highly resilient, efficient, and extensible.

## Versions

* **V1:** Initial implementation. Verbose JSON fields for every packet. High overhead.
* **V2:** Compact JSON fields. Reduced per-frame envelope size by ~65%.
* **V3 (Latest):** Zero-copy binary framing. Completely removes Base64 overhead, resulting in 25-33% higher effective throughput.

## V3 Binary Framing

Every V3 packet starts with a magic byte `0x50` ('P' in ASCII), followed by a Type byte.

### Manifest Packet (`Type 0x01`)

The Manifest describes the file being transferred and the structure of the incoming data stream.
In V3, it is transmitted in a highly compact binary format to ensure it fits in a single low-density QR code.

**Structure (Binary Layout):**
* `0x00`: Magic Byte (`0x50`)
* `0x01`: Packet Type (`0x01` = Manifest)
* `0x02`: Version (`0x03`)
* `0x03-0x17`: Transfer ID (21 bytes, NanoID)
* `0x18-0x1B`: Reserved / Timestamp (4 bytes)
* `0x1C-0x23`: Original Uncompressed Size (8 bytes, uint64)
* `0x24-0x27`: Total Data Packets (4 bytes, uint32)
* `0x28-0x29`: Total Parity Packets (2 bytes, uint16)
* `0x2A-0x2B`: Parity Group Size (2 bytes, uint16)
* `0x2C`: Parity Algorithm (`0x00` = None, `0x01` = XOR)
* `0x2D-0x2E`: Filename Length (2 bytes, uint16)
* `...`: Filename String
* `...`: MIME Type Length (1 byte)
* `...`: MIME Type String

*Note: Global SHA-256 is intentionally omitted from V3 Manifest to save space. Integrity relies on per-frame CRC32 and global Adler-32 decompression checksums.*

### Data & Parity Packets (`Type 0x02` & `Type 0x03`)

These packets contain the actual compressed file chunks or the erasure coding parity chunks.

**Structure (Binary Layout):**
* `0x00`: Magic Byte (`0x50`)
* `0x01`: Packet Type (`0x02` = Data, `0x03` = Parity)
* `0x02`: Version (`0x03`)
* `0x03-0x17`: Transfer ID (21 bytes, NanoID)
* `0x18-0x1B`: Packet Index (4 bytes, uint32)
* `0x1C-0x1F`: Total Packets in Stream (4 bytes, uint32)
* `0x20-0x23`: CRC32 of Payload (4 bytes, uint32)
* `0x24...`: Binary Payload

## Advanced Resilience (Erasure Coding)

Starting in Version 1.1, the protocol includes explicit Parity Packets to recover lost data without waiting for the QR loop to cycle.

### Forward Error Correction (FEC)
The default recovery algorithm is **XOR Parity**, configured in groups.

1. **Parity Grouping:** The compressed file stream is partitioned into groups of `N` packets (default `N=10`).
2. **Generation:** For each group, 1 Parity packet is generated by XORing the `N` data packets together.
3. **Transmission:** The Parity packet is appended to the stream.
4. **Recovery:** If exactly 1 packet (data) is lost within a group, the receiver automatically recovers the lost packet by XORing the remaining `N-1` packets with the Parity packet.

### Abstraction
The protocol allows swapping recovery algorithms via `RecoveryRegistry`. Future versions will introduce Reed-Solomon (for multi-packet loss recovery within a group) and Fountain Codes (for order-independent recovery).

## State Resumption
PrismTransfer supports pause/resume seamlessly across browser restarts.

* **Storage:** Packets are buffered into an `IndexedDB` backend via `idb`.
* **Manifests:** Active transfer sessions persist in `localStorage` and `IndexedDB`.
* **UI Banner:** Upon reopening the app, the user is prompted to resume an active transfer. Pre-credited packets are instantly loaded, and the scanner only listens for remaining unreceived packets.
